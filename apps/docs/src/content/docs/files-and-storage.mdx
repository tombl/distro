# Files and storage

A guest's files live in one of three places: the root image and the memory layer above it,
host directories you share with the guest, or disks you attach. This chapter covers each of
them, and how to get data from JavaScript into the guest and back.

## The mount table

Everything a guest mounts at boot comes from one list, the mount table, which works like
`/etc/fstab`. `image` is its entry at `/`, and `mounts` holds the rest:

```js
await using linux = await Linux.create({
  image: rootImage(),
  mounts: [
    { path: "/data", source: "data.ext4", mode: "rw" },
    { path: "/src", source: new NodeFS("./src"), mode: "ro" },
    { path: "/scratch", type: "tmpfs" },
  ],
});
```

Each entry has a `path`, and these fields:

- **`source`** is what to mount. A disk source becomes a block device: in Node.js a file path,
  and anywhere a `URL`, a `FileHandle`, bytes, a `Blob`, a `Response`, or a `BlockStorage`
  of your own. A filesystem backend such as `NodeFS` becomes a shared directory. Filesystems with
  no device, such as `tmpfs`, have no source.
- **`type`** is the filesystem type. Without one, the guest tries each type its kernel supports,
  as BusyBox `mount` does, and a shared directory is `virtiofs`.
- **`mode`** decides how the storage is opened and mounted. `"rw"`, the default, opens it
  writable and mounts it read-write. `"ro"` opens and mounts it read-only. `"overlay"` opens it
  read-only and mounts it beneath a writable layer in memory, so the guest can change its files,
  but the storage never changes and the changes last only until the machine ends or reboots.
- **`options`** is passed to the kernel as mount data, as `mount -o` would.

The guest mounts the root first, then a tmpfs at `/run` and `/tmp`, unless the table has an
entry there, then the other entries in order. Missing mount points are created. If a mount
fails, `Linux.create()` rejects with a `GuestBootError` that names the entry, and whose
`kernelLog` holds the end of the guest kernel's log, which usually says why.

The `-v` option of `lowland run` is a mount entry on the command line. A host directory is
shared and a regular file is attached as a disk. A trailing `:rw`, `:ro` or `:O` is the mode, `O`
standing for `"overlay"`:

```sh
npx lowland run -v ./src:/src:ro -v data.ext4:/data sh
```

## The root filesystem

`rootImage()` returns the mount entry `{ path: "/", source, type: "erofs", mode: "overlay" }`.
Programs can change any file, including in `/etc` and `/usr`, but every change is lost when the
machine ends. Every boot starts from the same files.

That suits the example service. Each snippet starts from a clean system, and nothing it does
outlives its machine. It also means that one image file can back any number of machines at
once.

To keep the root filesystem's changes, make the root an ext4 image in mode `"rw"`, such as
`image: { path: "/", source: "app.ext4", mode: "rw" }`, or `-v app.ext4:/` on the command line.
The [Your own software](/your-own-software/) chapter covers building one. A writable image
belongs to one machine at a time.

## Moving files in and out

`linux.fs` reads and writes files in the guest from JavaScript. Its methods look like those of
`node:fs/promises`, and they are carried out as system calls by the guest agent. They therefore
see exactly what programs in the guest see, with no cache in between, and they act as root.

The example service now accepts a set of files with the snippet, and returns the files the
snippet produced:

```js
await linux.fs.mkdir("/work");
for (const [name, contents] of Object.entries(files)) {
  await linux.fs.writeTextFile(`/work/${name}`, contents);
}

const process = await linux.spawn(["sh", "-c", code], { cwd: "/work" });
// ...wait for it as before...

const outputs = {};
for await (const entry of linux.fs.readDir("/work")) {
  if (entry.isFile) outputs[entry.name] = await linux.fs.readTextFile(`/work/${entry.name}`);
}
```

Failures reject with a `SystemError` whose `code` is the errno name, such as `"ENOENT"` or
`"EISDIR"`.

`writeFile()` also accepts a `ReadableStream`, so a download can go straight into the guest
without being held in memory on the host:

```js
const response = await fetch("https://example.com/data.tar.gz");
await linux.fs.writeFile("/work/data.tar.gz", response.body);
```

Each call is at least one round trip to the guest. For a large tree of small files, send one
archive and unpack it inside the guest instead:

```js
await linux.run(["tar", "-xz", "-C", "/work"], { input: archive }); // the .tar.gz as bytes or a stream
```

The same works in reverse with `tar -c` and the result's `stdout`.

## Sharing a host directory

A shared directory gives the guest live access to files on the host, with no copying. Its
`source` is a filesystem backend: `NodeFS` from `lowland/node` in Node.js, or `BrowserFS` from
`lowland/browser` in a browser.

```js
import { NodeFS } from "lowland/node";

const mounts = [{ path: "/project", source: new NodeFS("./project", { readOnly: true }), mode: "ro" }];
```

In a browser, `new BrowserFS(handle)` serves a `FileSystemDirectoryHandle`, such as a folder the
user picked with `showDirectoryPicker()` or the origin private file system.

Some behavior to know before you rely on it:

- **Read-only belongs to the backend.** Mode `"ro"` mounts the share read-only, but a guest
  running as root can mount it again read-write. Pass `readOnly: true` to `NodeFS` as well, and
  the host refuses writes with `EROFS`. `lowland run -v dir:/dst:ro` does both.
- **The guest caches metadata.** File attributes and name lookups are cached for one second.
  Directory listings are always read fresh. If other host programs change files while the guest
  runs, attach the share yourself with `fileSystemDevice(fs, { tag, cache: false })` from
  `lowland/machine`, as [The layers beneath](/layers/#devices-the-mount-table-does-not-cover)
  shows. File contents the guest has read can still be cached.
- **`BrowserFS` emulates POSIX.** The browser file system API has no permissions, ownership or
  atomic rename. `BrowserFS` keeps modes, owners and timestamps in memory, so they reset when
  you create a new `BrowserFS`. Rename copies and then deletes, so one that fails partway can
  lose the old destination, leave a partial new one, or leave both names. The
  [reference](/reference/guest/#BrowserFS) has the details.
- **`NodeFS` confines paths, within limits.** It keeps the guest inside the shared directory,
  but cannot guarantee that while another host process moves things around in it. Share a
  directory that your application owns.

## Keeping data between runs

To keep data, attach a disk whose storage lives on the host, in mode `"rw"`. In Node.js the
source can be a path to an image file. In a browser, it can be a file in the origin private file
system (OPFS).

### In Node.js

Make the disk an ext4 image, for example with `lowland build --format ext4`, and mount it:

```js
const mounts = [{ path: "/data", source: "data.ext4", mode: "rw" }];
```

The file is read and written in place, as the guest needs blocks.

### In a browser

Fast access to an OPFS file is only available in a dedicated worker, through
`createSyncAccessHandle()`. That makes it a device rather than a mount table source. The worker
serves the disk with `serveDevice()`, and the page attaches it with `workerDevice()` as a plugin:

```ts title="disk-worker.ts"
import { blockDevice, type BlockStorage, serveDevice, serveDeviceError } from "lowland/machine";

const capacity = 256 * 1024 * 1024;

async function openStorage(): Promise<BlockStorage> {
  const directory = await navigator.storage.getDirectory();
  const file = await directory.getFileHandle("disk.img", { create: true });
  const access = await file.createSyncAccessHandle();
  if (access.getSize() === 0) access.truncate(capacity);

  return {
    capacity: access.getSize(),
    read(offset, target) {
      let done = 0;
      while (done < target.byteLength) {
        const n = access.read(target.subarray(done), { at: offset + done });
        if (n === 0) break;
        done += n;
      }
      return done;
    },
    write(offset, data) {
      let done = 0;
      while (done < data.byteLength) {
        const n = access.write(data.subarray(done), { at: offset + done });
        if (n === 0) break;
        done += n;
      }
      return done;
    },
    flush() {
      access.flush();
    },
    close() {
      access.flush();
      access.close();
    },
  };
}

try {
  serveDevice(self, blockDevice(await openStorage(), { serial: "data" }));
} catch (error) {
  serveDeviceError(self, error);
}
```

```ts title="page.ts"
const worker = new Worker(new URL("./disk-worker.ts", import.meta.url), { type: "module" });
const disk = await workerDevice(worker);
disk.closed.finally(() => worker.terminate());

await using linux = await Linux.create({ image: rootImage(), plugins: [disk] });
```

`read` and `write` receive views straight into guest memory, valid until the call returns, so
data is never copied on the host. Loop until the whole view is done, because the guest treats a
short transfer as an I/O error. If the worker calls `serveDeviceError()`, `workerDevice()`
rejects with an `Error` of the same `name` and `message`.

`truncate()` reserves the full capacity against the origin's storage quota at once, and a file
that already exists keeps its size. Pick the capacity before the first run.

### Format and mount it

A disk attached as a plugin is an ordinary block device in the guest, not yet mounted.
`linux.guest.disk(serial)` finds its device node by the serial the worker gave it. A new disk
contains only zeros, so make a filesystem on first use:

```js
const device = await linux.guest.disk("data");
const probe = await linux.run(["blkid", device]);
if (probe.stdout.byteLength === 0) {
  await linux.run(["mkfs.ext2", device]);
}
await linux.fs.mkdir("/data");
await linux.guest.mount(device, "/data", { type: "ext2" });
```

Serials beginning with `m` and a number are taken by the mount table's own disks.

### Don't lose writes

The guest kernel holds recent writes in its page cache and writes them out later. `shutdown()`
and `await using` have the guest agent sync and unmount every filesystem first. `kill()`, a
deadline that kills, or a tab that closes discards whatever has not been written yet, and can
leave the filesystem inconsistent. If a machine may be killed, call `linux.fs.sync()` after
writes that matter.

A browser tab can close at any moment, so sync after writes that matter, or mount with
`options: "sync"` and accept slower writes. Ask for durable storage with
`navigator.storage.persist()`, or the browser may evict the file under storage pressure.

An ext4 disk that was not unmounted cleanly needs its journal recovered. It still mounts in mode
`"rw"`, which recovers it, but mode `"ro"` or `"overlay"` fails, because read-only storage cannot
be recovered.

### One tab at a time

Only one sync access handle can be open on an OPFS file. While one tab has the disk open,
`createSyncAccessHandle()` in another throws a `NoModificationAllowedError`, which reaches the
page as a rejection with that `name`. Tell the user the page is open elsewhere, or give each
tab its own file.
