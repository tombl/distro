# Attach a terminal

This guide connects a guest's console to [xterm.js](https://xtermjs.org/) and starts an
interactive shell on it. It assumes a page set up as in
[Set up a browser page](/set-up-a-browser-page/), and the root device and guest agent from the
[`@lowland/guest` usage example](/reference/guest/#usage).

## The console device

`consoleDevice(input, output)` from `@lowland/kernel` adds a console to the machine. The guest
sees it as `/dev/hvc0`.

- `input` is a `ReadableStream<Uint8Array>` of the bytes a keyboard would send.
- `output` is a `WritableStream<Uint8Array>` of the bytes a terminal should display.

Either may be `null`. For example, `consoleDevice(null, output)` is a console that only shows
output.

The guest kernel handles echo, line editing, and Ctrl+C, so the page only moves bytes. The
console starts at 80 columns by 24 rows. `device.resize(columns, rows)` changes its size and
sends `SIGWINCH` to the program in the foreground, so full-screen programs redraw.

Kernel messages printed after the console starts also appear on it. Earlier boot messages are
discarded unless you add the `bootConsole(output)` plugin, which writes them to a stream of
your choice. This is useful when a machine fails early in boot.

## Connect xterm.js

xterm.js reports keyboard input as strings and accepts output as bytes or strings. Encode the
input, and resolve each output write only when xterm.js has processed it:

```ts
import { Terminal } from "@xterm/xterm";
import { consoleDevice } from "@lowland/kernel";

const terminal = new Terminal({ convertEol: true });
terminal.open(document.querySelector("#terminal")!);

const input = new ReadableStream<string>({
  start(controller) {
    terminal.onData((data) => controller.enqueue(data));
  },
}).pipeThrough(new TextEncoderStream());

const output = new WritableStream<Uint8Array>({
  write(data) {
    return new Promise<void>((resolve) => terminal.write(data, resolve));
  },
});

const tty = consoleDevice(input, output);
terminal.onResize(() => tty.resize(terminal.cols, terminal.rows));
tty.resize(terminal.cols, terminal.rows);
```

Waiting for the write callback means the guest slows down when xterm.js falls behind, instead
of output piling up in the page. `convertEol: true` makes xterm.js treat each `\n` from the
guest as a new line. On input, xterm.js already sends Enter as `\r`, which is what the
console expects.

If you size the terminal with `@xterm/addon-fit`, a call to `fit()` that changes the size fires
`onResize`, so the console follows the terminal.

Add the device to the machine with the guest agent:

```ts
const guest = guestAgent();
const machine = await bootMachine({ cpus: 1, plugins: [root, guest, tty] });
```

## Start a shell

Unless the image starts something on the console, as described below, nothing runs there until
you start it. Run a shell with its input and output on
`/dev/hvc0`, and start a new one whenever it exits:

```ts
for (;;) {
  const shell = await guest.exec(
    ["sh", "-c", "clear >/dev/hvc0; exec setsid cttyhack sh </dev/hvc0 >/dev/hvc0 2>&1"],
    { env: { TERM: "xterm-256color" } },
  );
  await shell.status;
  await new Promise((resolve) => setTimeout(resolve, 100));
}
```

`setsid cttyhack` gives the shell `/dev/hvc0` as its controlling terminal. Without a
controlling terminal, Ctrl+C cannot interrupt the running program. Because the loop starts a
new shell, typing `exit` clears the screen and shows a fresh prompt. The short delay stops a
shell that fails immediately from restarting in a tight loop. `TERM=xterm-256color` tells
full-screen programs which escape sequences xterm.js supports.

An image can start the shell itself instead. If the root image has an executable `/init`, the
guest agent starts it with the console as its standard input and output. The machine powers
off when `/init` exits, so a script that ends with `exec setsid cttyhack sh` keeps a shell on
the console for the life of the machine.
